# Redis: кэширование и маршрутизация задач

Статус: дизайн-план (не реализован). Цель — убрать долгие ИИ-вызовы из
синхронного контура запроса и снизить нагрузку на LLM-провайдер за счёт
кэша. Целевой стек: `redis:7-alpine` в том же Docker Compose-контуре,
брокер задач — **arq** (asyncio, хорошо ложится на FastAPI; альтернатива —
Celery, см. раздел 7).

## 1. Текущее состояние (точка отсчёта)

- `POST /api/ai/generate` (main.py, ~стр. 1048) — генерация BPMN + скоринг
  выполняются синхронно в обработчике запроса.
- `POST /api/ai/improve` (main.py, ~стр. 1098) — `await
  bpmn_processor.improve_diagram(...)`: RAG по корпусу
  `core/bpmn_dataset/` + вызов внешней LLM (GigaChat);
  результат складывается в `pending_improvements` и ждёт апрува.
- ИИ-ядро (`core/llm_improve.py`) поднимает тяжёлые модели (эмбеддинги
  sentence-transformers, TF-IDF-векторизатор; векторного индекса нет —
  поиск считается по numpy) один раз при старте процесса
  (`BPMNImprovementOrchestrator()` в модуле `main`).
- Очередей задач нет: один медленный запрос занимает воркер uvicorn;
  повторные одинаковые запросы заново ходят в LLM.

Проблемы: таймауты клиентов и прокси (30–60 с) на долгой генерации,
нет защиты от дублей, платные токены тратятся на идентичные запросы,
невозможно ограничить параллельные обращения к LLM.

## 2. Redis в docker-compose.yml

Сервис только во внутренней сети (порт наружу не публикуется, по аналогии
с `db`):

```yaml
  redis:
    image: redis:7-alpine
    restart: unless-stopped
    command: ["redis-server", "--appendonly", "yes", "--maxmemory", "512mb", "--maxmemory-policy", "allkeys-lru"]
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10
```

- `appendonly yes` — переживает рестарт контейнера (очередь задач не
  теряется). Для чистого кэша хватило бы RDB, но у нас и очередь.
- `maxmemory` + `allkeys-lru` — защита от разрастания кэша; задачи
  (списки/стримы) держать в отдельных ключах с гарантированной
  обработкой, а не только в кэше (см. раздел 4.4).
- В `backend` и `worker` добавить `depends_on: redis: condition:
  service_healthy` и переменную `REDIS_URL=redis://redis:6379/0`.
- Имя базы данных в `REDIS_URL` разделяет назначения: `/0` — очередь,
  `/1` — кэш (можно сбрасывать `FLUSHDB` независимо).

## 3. Кэширование

### 3.1 Что кэшируем и зачем

| Объект | Ключ | TTL | Инвалидация |
|---|---|---|---|
| Ответ LLM на улучшение схемы | `llm:improve:{model}:{sha256(xml + prompt_version + params)}` | 7 дней | при изменении промпта/модели меняется `prompt_version`; ручная очистка `DEL` |
| Ответ LLM на генерацию | `llm:generate:{model}:{sha256(prompt)}` | 24 ч | тот же механизм |
| Результат rule-based скоринга | `score:{sha256(xml)}` | 30 дней | скоринг детерминирован, инвалидация только при смене правил (версия правил в ключе) |
| Векторный индекс RAG | НЕ в Redis | — | остаётся в памяти процесса / в pickle-кэшах `core/`; Redis для него не нужен |

Правила:

1. Ключ строится только из входов, влияющих на результат (модель,
   версия промпта, хэш текста). Никаких `user_id` в ключе кэша
   результатов — но доступ к кэшу только через авторизованные эндпоинты.
2. Кэшируем только успешные ответы. Ошибки провайдера не кэшируются.
3. Значение — JSON: `{result, model, created_at, prompt_version}`;
   при чтении проверяем `prompt_version`, устаревшие игнорируем.
4. Формат значений — только через `pydantic`-схемы, чтобы кэш не стал
   источником «сырых» данных в обход валидации.
5. Отрицательные результаты (например, валидация не прошла) можно кэшировать
   отдельно с коротким TTL (5 мин), чтобы не «долбить» провайдера
   повторами заведомо плохого XML.

### 3.2 Где вставлять кэш

Один тонкий слой-обёртка `core/llm_cache.py`:

```python
class LLMCache:
    def __init__(self, redis: Redis, namespace: str): ...
    async def get_or_none(self, key: str) -> dict | None: ...
    async def set(self, key: str, value: dict, ttl: int): ...
```

Вызывается в `core/llm_improve.py` и в эндпоинте генерации ДО обращения к
провайдеру и после успешного ответа. Никакой логики кэша в роутерах.

### 3.3 Что НЕ кэшируем

- Апрувы и `pending_improvements` — состояние в PostgreSQL.
- Сессии/JWT — они и так стате-фри (подпись). Не вводить серверные
  сессии ради кэша.
- Персональные подборки/реестр — читаются из БД; при росте нагрузки
  добавить кэш списков с инвалидацией по записи, а не глобальный.

## 4. Маршрутизация задач

### 4.1 Схема

```
браузер → POST /api/ai/improve → backend пишет задачу в Redis
                                     → сразу возвращает {task_id, status: queued}
worker (arq) берёт задачу → кэш? → нет → LLM → запись результата в БД и в статус задачи
браузер → GET /api/tasks/{task_id} → статус/результат (опрос; позже — SSE)
```

### 4.2 Очереди и приоритеты

Две очереди, у воркера разные лимиты параллелизма:

| Очередь | Задачи | Параллелизм | Таймаут задачи | Ретраи |
|---|---|---|---|---|
| `ai_llm` | improve, generate | 2 (лимит на внешнее API) | 180 с | 2, экспоненциальный backoff 5/25 с |
| `ai_local` | scoring, LLM-валидация без внешних вызовов | 4 | 60 с | 1 |

Маршрутизация = выбор очереди при постановке (`queue_name=` в arq).
Никаких «умных» правил маршрутизации сверх этого пока не нужно:
очередь определяет тип нагрузки, а не бизнес-логика.

### 4.3 Контракт задачи

- Идентификатор: `task_id = uuid4`. Дублируем в таблице БД
  `ai_tasks(id, user_id, kind, status, created_at, finished_at,
  error, result_ref)` — Redis лишь транспорт; источник истины — БД.
  Это также даёт пользователю историю задач.
- Статусы: `queued → running → done | failed | cancelled`.
  Статус держим в `ai_tasks` (БД), в Redis — только горячее состояние
  воркера. Опрос клиентом идёт через БД-эндпоинт.
- Идемпотентность: клиент может передать `idempotency_key`;
  `SETNX ai:idem:{user}:{key}` с результатом `task_id` — повторная
  отправка возвращает ту же задачу, а не создаёт новую.
- Аргументы задачи — только идентификаторы (`diagram_id`, `user_id`),
  не содержимое: воркер сам читает схему из БД. Это исключает гонку
  «задача создана по старой версии схемы» меньше, чем передача снапшота;
  осознанный выбор — фиксируем версию схемы в задаче полем
  `diagram.updated_at` на момент постановки и проверяем при выполнении.

### 4.4 Требования к надёжности

- Воркер идемпотентен по `task_id`: перед выполнением переводит задачу
  в `running` условным обновлением (`WHERE status='queued'`); если не
  получилось — задачу уже взяли.
- `ack` результата — после записи в БД (сначала БД, потом завершение
  задачи в очереди).
- При старте воркера: задачи в `running` старше таймаута возвращаются
  в `queued` (защита от падения воркера посреди выполнения).
- Отмена: `POST /api/tasks/{task_id}/cancel` ставит флаг в БД; воркер
  проверяет флаг перед обращением к LLM (не прерывает уже идущий вызов).

### 4.5 Изменения в коде (порядок)

1. `requirements.txt`: `redis`, `arq`.
2. Новый модуль `core/tasks.py`: настройки RedisSettings, функции задач
   (`improve_diagram_task`, `generate_bpmn_task`, `score_task`),
   реестр `WorkerSettings` (очереди, ретраи, таймауты).
3. `main.py`: эндпоинты `POST /api/ai/improve` и `POST /api/ai/generate`
   переводятся на постановку задачи и возврат `202 + {task_id}`;
   новый `GET /api/tasks/{task_id}`. Совместимость со старым контрактом
   не поддерживать — фронтенд меняется синхронно (внутренний продукт).
4. `bpmn-constructor`: вместо ожидания ответа — опрос статуса раз в 2 с
   с экспоненциальным замедлением до 5 с; таймаут сценария 5 мин.
5. `docker-compose.yml`: сервис `worker` из того же образа `backend`
   с `command: ["arq", "core.tasks.WorkerSettings"]` и общим `static/`
   (если экспорт файлов делает воркер).
6. `SKIP_LLM_INIT` не нужен для веб-процесса после выноса:
   `bpmn_processor` живёт только в воркере. Это заметно ускорит старт
   `backend` и позволит держать `bpmn_processor` в одном экземпляре.

## 5. Переменные окружения

В `.env.example` / compose:

```
REDIS_URL=redis://redis:6379/0        # очередь (бэкенд и воркер)
CACHE_REDIS_URL=redis://redis:6379/1  # кэш
LLM_CACHE_TTL=604800                  # 7 дней, ответы улучшения
GENERATION_CACHE_TTL=86400
ARQ_MAX_JOBS=2                        # параллельные LLM-вызовы
```

## 6. Поэтапный план внедрения

1. **Этап A — только кэш** (малый риск, без изменения контрактов):
   сервис `redis` в compose, `core/llm_cache.py`, кэш в улучшении и
   генерации. Контракты эндпоинтов не меняются. Проверка: повторный
   одинаковый запрос улучшения возвращается быстрее и без обращения к
   провайдеру (видно по логам).
2. **Этап B — очередь и воркер**: таблица `ai_tasks`, `core/tasks.py`,
   сервис `worker`, асинхронный контракт эндпоинтов, опрос на фронтенде.
   Проверка: два одновременных запроса улучшения не удваивают нагрузку
   на провайдер (лимит `ARQ_MAX_JOBS`), падение воркера не теряет
   задачу (перезапуск контейнера → задача довыполняется).
3. **Этап C — улучшения по итогам**: отмена задач, SSE вместо опроса,
   метрики (время в очереди, доля кэш-попаданий), алерт на растущую
   очередь.

Каждый этап завершается проверкой наблюдаемого поведения (по рабочему
порядку проекта) и обновлением этой документа.

## 7. Почему arq, а не Celery (и когда наоборот)

- **arq**: asyncio из коробки, один лёгкий процесс, естественен для
  FastAPI; достаточно для десятков задач в минуту (масштаб этой
  платформы). Итоговая рекомендация на сегодня.
- **Celery**: понадобится, если появятся (а) синхронные тяжёлые
  CPU-задачи, которые надо изолировать в отдельные процессы,
  (б) требования к приоритетным очередям сложной формы, ретраям с
  планировщиком (beat) и зрелой экосистемой мониторинга (Flower).
  Переход потребует переписать `core/tasks.py`, но контракт задач
  (раздел 4.3) останется тем же.

## 8. Риски и ограничения

- Кэш ответов LLM может отдавать устаревшую рекомендацию после смены
  промпта — решается версией промпта в ключе (раздел 3.1, п. 3).
- `appendonly` без ограничений размера — следить за `maxmemory` и
  периодическим `BGREWRITEAOF`.
- Redis в одном экземпляре — единая точка отказа для очереди. Для этого
  контура допустимо (задачи не теряются благодаря AOF; при желании —
  `redis:7-alpine` + replica позже). Статусы задач в БД, поэтому
  пользовательский интерфейс деградирует мягко.
- Не хранить в Redis персональные данные сверх идентификаторов:
  содержимое схем живёт в БД, в кэше — только хэшированные ключи и
  технические ответы модели.
