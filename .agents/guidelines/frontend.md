# Frontend Rules

## Когда использовать

Открывай этот файл при задачах по web-интерфейсу, навигации, редактору
схем, состоянию клиента, работе с API и проверке экранов.

## Основной контекст

Frontend расположен в `bpmn-constructor/` и собирается как React-приложение
(Create React App, React 19, react-router v7). Редактор схем — `bpmn-js`
с панелью свойств и авто-раскладкой. Стили — комбинация компонентных
библиотек и собственных стилей.

Известная особенность: в проекте соседствуют несколько UI-наборов
(Chakra UI, PrimeReact, MUI, наборы иконок). Не добавляй четвёртый подход
или новую библиотеку стилей: переиспользуй то, что уже есть на экране,
который правишь; для нового экрана выбирай один из уже используемых.

## Актуальные маршруты

- `/` — главная (вход в продукт);
- `/login`, `/register` — аккаунт;
- `/editor` — редактор схем (генерация, скоринг, улучшение, апрув);
- `/my-schemas` — реестр: мои схемы, папки, команды, удалённые;
- `/guideline` — гайдлайны моделирования;
- `/errors` — типовые ошибки BPMN;
- `/profile` — профиль пользователя.

Защищённые маршруты обёрнуты в `ProtectedRoute`. Компонент `InviteAccept`
существует, но маршрут принятия приглашения в `App.js` не подключён — при
работе с приглашениями проверь фактическое состояние роутинга.

## Сеть и API

- Базовый адрес задаётся в `src/config.js` (`REACT_APP_API_URL`,
  по умолчанию `http://localhost:8765`) и подключается глобально через
  `axios.defaults.baseURL` в `index.js`. Компоненты используют
  относительные пути `/api/...`; не возвращай в код абсолютные литералы
  с адресом сервера.
- Токен передаётся глобальным заголовком `Authorization: Bearer`
  (устанавливается в `AuthContext`).
- Для новых запросов учитывай таймауты и состояния загрузки/ошибки;
  долгие ИИ-операции (генерация, улучшение) должны показывать прогресс.

## Состояние и хранение

- `localStorage` хранит только токен сессии; не добавляй туда серверные
  данные (реестр, команды, схемы).
- Считай содержимое `localStorage` недоверенным; после `401` очищай
  сессию через `logout()`.
- Открытая в редакторе схема — локальное рабочее состояние; источник
  истины — сервер (`/api/diagrams/{id}`).

## Редактор и ИИ-сценарии

- `Editor` — центральный экран: загрузка схемы, генерация по описанию,
  скоринг (панель оценки), улучшение через чат и принятие улучшений.
- Генерация и улучшение используют чат-интерфейсы (`GenerateChat`,
  `ImproveChat`); авто-раскладка применяется к сгенерированному XML.
  Раскладку вызывает `layoutDiagram` из `src/bpmnLayout.js`, а не
  `layoutProcess` напрямую: `bpmn-auto-layout` падает на части корректных
  многупуловых схем (messageFlow с источником-задачей), а без координат
  `bpmn-js` показывает пустой холст.
- Любая правка ИИ-потока в редакторе должна сохранять явный шаг апрува:
  пользователь видит предложенные изменения и принимает их осознанно.
- Работу с `bpmn-js` (modeler, moddle, свойства элементов) веди через
  существующие обёртки; не дублируй прямые вызовы библиотеки по файлам.

## Направляющие вопросы для frontend

Используй как опору, а не обязательный алгоритм.

1. Какую задачу решает пользователь и что он должен увидеть или сделать
   в первую очередь?
2. Понятны ли без изучения реализации назначение экрана, текущее
   состояние, главное действие и ожидаемый результат?
3. Как выглядит экран при 0, 1, 5 и 20+ схемах/папках/рекомендациях?
4. Что произойдёт с длинными названиями, отсутствующими полями, ошибкой
   сети и недоступным ИИ?
5. Остаются ли ключевой результат и основное действие доступными при
   загрузке и обновлении данных? Не скачет ли layout?
6. Можно ли переиспользовать существующий компонент вместо нового?
7. Показаны ли состояния загрузки, ошибки, пустого результата?
8. Проверен ли сценарий в браузере на реалистичных данных?

## Проектирование для пользователя

Платформа — рабочий операционный продукт для специалистов ВкусВилл,
которые регулярно описывают, редактируют и улучшают бизнес-процессы.

- Делай основные сценарии (создать схему, оценить, улучшить, поделиться)
  короткими и предсказуемыми.
- Отдавай приоритет сканированию реестра, сравнению версий схемы
  и повторяющимся операциям.
- Используй спокойную, утилитарную композицию без декоративной
  маркетинговой стилизации на рабочих экранах.
- Реализуй состояния функции целиком: загрузка, пустой результат, ошибка,
  ограничение доступа, успех и повторное действие.

## Операционный viewport

- На обычном desktop-viewport ключевое состояние и основное действие
  должны быть видны без вертикальной прокрутки.
- Длинные списки (реестр, рекомендации, история) размещай во внутренних
  прокручиваемых областях или вкладках; у страницы один основной
  вертикальный скролл.
- Не решай проблему высоты нечитаемым текстом или удалением нужных
  подписей.

## Текст и термины

- Используй термины пользователя: «схема», «процесс», «оценка»,
  «улучшение», «команда», «доступ». Не выводи имена компонентов,
  endpoint-ов, таблиц и внутренних этапов.
- Ошибка должна кратко объяснять последствие и следующий шаг; не показывай
  пользователю стектрейсы и диагностические коды.

## Адаптивность и состояния

- Проверяй интерфейс минимум на узком мобильном и обычном desktop
  viewport.
- Hover-состояние не должно быть единственным способом получить
  информацию или выполнить действие.
- Фокус должен быть заметен при клавиатурной навигации.

## Проверка результата

После заметного изменения интерфейса:

1. Запусти `npm start` в `bpmn-constructor/` (dev-сервер на `:3456`, backend на `:8765`).
2. Проверь основной пользовательский сценарий от действия до результата.
3. Проверь состояния загрузки, ошибки, пустого и заполненного результата.
4. Для изменений редактора проверь рендер схемы, авто-раскладку,
   сохранение и общий доступ.
5. Если браузерная проверка невозможна, явно укажи это в финальном ответе.

## Документация frontend

- Перечисляй функции продукта, а не имена файлов.
- Не добавляй в навигацию раздел, которого нет среди актуальных маршрутов.
- Не выдавай внутренний механизм за пользовательский экран.
