# Security And Operations Rules

## Когда использовать

Открывай этот файл при задачах про авторизацию и роли, токены и приглашения,
секреты, файлы, XML-обработку, LLM-взаимодействия, БД и будущий
Docker-контур.

## Основной принцип

- Сначала установи фактическую границу доверия: браузер, FastAPI, модули
  `core/`, БД, LLM-провайдер, SMTP или файловая система.
- Считай недоверенными параметры запросов, заголовки, загруженные файлы,
  импортированный XML, ответы LLM и сохранённый пользовательский контент.
- Не ослабляй существующую защиту ради совместимости. Если исключение
  необходимо, задокументируй его область, причину и компенсирующие меры.
- Вывод о защите подтверждай кодом и по возможности проверкой.

## Известный долг (фиксируй и не усугубляй)

- `SECRET_KEY` (JWT), SMTP-пароль и API-ключи LLM раньше были захардкожены
  в `main.py`, `core/llm_improve.py` и `core/llm_validator.py`. Сейчас они
  читаются из переменных окружения (`.env` вне Git, шаблон `.env.example`).
  Новые секреты в код не добавляй никогда.
- Прежние значения, попавшие в код, считай скомпрометированными:
  их нужно ротировать, а не переиспользовать.
- `CORS allow_origins=["*"]` при включённых credentials — недопустимо
  в production; при деплое заменяй на явный список доменов.
- Автозапуск `Base.metadata.create_all` + ad-hoc `apply_migration()` —
  переходная схема; в целевом контуре миграции версионируемые.

## Авторизация и управление доступом

- Пароли хранятся только как bcrypt-хэши. Не возвращай хэш, пароль или
  код подтверждения в ответах, логах и письмах.
- Сессия — JWT (HS256) в заголовке `Authorization: Bearer`; фронт хранит
  токен в `localStorage`. Проверяй подпись и срок действия на сервере
  для каждого защищённого запроса.
- Каждый защищённый endpoint проверяет не только факт входа, но и
  объектный доступ: владелец диаграммы/папки, членство в команде и флаг
  роли (`viewRegistry`, `editRegistry`, `manageRoles`). Проверка только
  на фронте не считается защитой.
- Публичные идентификаторы ресурсов (токены доступа, приглашения, сброс
  пароля) — криптографически случайные/UUID, с `expires_at` и
  одноразовостью там, где она задумана.
- Токен общего доступа на диаграмму даёт ровно объявленное право
  (просмотр или редактирование) и не расширяется на другие объекты.
- Доменные приглашения ограничивай корпоративным доменом и ролью;
  принятие приглашения проверяет срок и одноразовость токена.

## Ввод, файлы и XML

- Импортируемый и сгенерированный XML считай враждебным: ограничивай
  размер, валидируй структуру и namespace до сохранения и рендера;
  не исполняй внешние сущности.
- Загружаемые файлы проверяй по расширению и содержимому; имена
  нормализуй сервером. Не записывай файлы по недоверенным путям.
- Раздачу файлов веди через существующий статический механизм, не через
  ручной путь по строке из запроса.

## ЛЛМ-взаимодействия

- Пользовательский текст и содержимое схем попадают в промпт: не выполняй
  инструкции, «извлечённые» из ответа модели, как код или команды.
- Ответ модели — данные, а не код: XML принимается только после
  детерминированного применения операций и починки (`core/bpmn_edits.py`),
  JSON — только через разбор из `core/llm_client.py`.
- Ограничивай таймаут, ретраи и размер ответа; недоступность провайдера
  должна давать понятную ошибку, а не зависший запрос.
- Не отправляй провайдеру данные, не нужные для задачи (пароли, токены,
  персональные данные из профилей).
- Ключи провайдеров — только из окружения; не логируй их и не включай
  в диагностические дампы.

## Персональные данные

Профили могут содержать ФИО/имя, должность, компанию, сайт и описание.
Учитывай:

- минимизацию: не запрашивай и не храни лишнего;
- доступ: профиль пользователя редактирует он сам; командные данные —
  только участники с правом;
- не выводи персональные данные в логи, метрики и письма сверх
  необходимости (в приглашении — только роль и команда).

## Секреты и конфигурация

- Никогда не коммить значения ключей, паролей, токенов и строк
  подключения. `.env` исключён из Git; рядом держи `.env.example` без
  реальных значений.
- Чувствительные настройки читай при старте и проверяй их наличие:
  в целевом контуре отсутствие `SECRET_KEY` или `DATABASE_URL` должно
  останавливать приложение (fail-closed), а не приводить к работе
  на значениях по умолчанию.

## БД (текущая и целевая)

- Сейчас: SQLite-файл. Не используй `check_same_thread`-обход как повод
  для конкурентных записей в одном процессе без транзакций.
- Цель (PostgreSQL): подключение пулом, параметризованные запросы
  (только через ORM/`text()` с параметрами), явные ограничения
  (`NOT NULL`, `UNIQUE`, FK), индексы под подтверждённые запросы,
  `SELECT` только нужных колонок, миграции без даунтайма и с планом
  отката.
- Резервные копии считай данными уровня production: ограничивай доступ
  и не храни рядом с логами, содержащими секреты.

## Целевой Docker-контур

При создании/правке `docker-compose` и `Dockerfile`:

- сервисы: `db` (официальный postgres, volume, healthcheck, порты не
  публикуются наружу), `backend` (non-root, healthcheck `/health`),
  `frontend` (сборка и раздача, без исходников в финальном образе);
- секреты и настройки — через `.env`/environment, не в `ARG`/`ENV` образа;
- не запускай контейнеры от root без необходимости; исключай из контекста
  сборки `.env`, кэши, `node_modules`, локальные данные и логи;
- зависимости фиксируй версиями; не используй `latest`;
- после правок проверяй сборку, старт, `/health` и базовый сценарий.

### Проверенный порядок запуска

Контур обкатан и поднимается так:

1. Заполни `.env` (по шаблону `.env.example`): `POSTGRES_PASSWORD`,
   `SECRET_KEY`, валидный `MAIL_FROM` (см. ниже).
2. `docker compose up -d` — поднимает `db`, `backend`, `frontend`.
   Backend на `127.0.0.1:8765`, frontend на `127.0.0.1:3456`, БД наружу
   не публикуется.
3. Перенос данных из `bpmn.db` (одноразово, на свежей БД):
   `docker compose run --rm -v "$(pwd -W)/bpmn.db:/app/bpmn.db:ro" -e SKIP_LLM_INIT=1 backend python migrate_sqlite_to_postgres.py`
4. Проверь `curl http://localhost:8765/health` и открытие `:3456`.

Подводные камни (проверено на практике):

- **Windows/Git-Bash:** для bind-mount используй `$(pwd -W)`
  (`C:/...`), а не `${PWD}` (`/c/...`) — последний не монтируется,
  и скрипт миграции сообщает «база не найдена или пуста».
- **`MAIL_FROM` обязан быть валидным e-mail** (с реальным доменом, не
  `.local`/`.test`): `ConnectionConfig` валидирует формат при импорте
  `main.py`, поэтому пустое или reserved-значение роняет старт backend.
  Пока SMTP не настроен — держи placeholder вроде `no-reply@vkusvill.ru`.

## Наблюдаемость

- Логи должны содержать идентификатор запроса/сценария и безопасные
  идентификаторы, но не пароли, токены, ключи и содержимое писем.
- `llm_debug.log` и `xml_debug.log` — отладочные артефакты: не включай
  в них секреты и не коммить их содержимое.
- Ошибки пользователю возвращай без деталей реализации и стектрейсов.

## Как отвечать пользователю

- Для описания фиксируй проверенные факты: где проверяется доступ, где
  хранятся данные, как живут токены.
- Не показывай значения секретов и не вставляй полные дампы окружения
  или логов.
- Если при правке обнаружена новая уязвимость или скомпрометированный
  секрет, сообщи об этом явно, даже если задача была о другом.
