# Testing Rules

## Когда использовать

Открывай этот файл при изменениях кода, API, UI-потоков, скоринга,
генерации, улучшения схем, авторизации, команд или сохранения данных.

## Общий принцип

Проверка должна соответствовать риску изменения и доказывать наблюдаемое
поведение пользователя. Документационной правке достаточно поисковой
проверки; изменению бизнес-логики нужен прогон затронутого сценария
или явное объяснение, почему его невозможно выполнить.

Автоматические проверки есть: `python -m pytest tests/ -q` из корня
проекта (разбор ответов LLM, аплайер операций, скоринг, HTTP-контур
улучшения/принятия, оркестратор с подставленным транспортом LLM).
Сеть и ключ провайдера для прогона не нужны. Покрытые сценарии не
дублируй ручным прогоном; для нового стабильного бизнес-правила
(скоринг, апрув, доступ) добавь тест в `tests/`, а не только ручной
прогон.

## Core Boundary: Ядро кода

Правки поведения в следующих путях являются high-impact:

- `main.py` — API, модели, авторизация, команды и хранение;
- `core/bpmn_generator.py` — генерация схем;
- `core/bpmn_scoring.py` — правила скоринга;
- `core/llm_improve.py` — оркестратор улучшения и RAG;
- `core/llm_client.py` — транспорт LLM, ретраи и разбор ответа;
- `core/bpmn_edits.py` — применение операций и починка XML;
- `bpmn-constructor/src/context/AuthContext.js` — сессия и токен;
- `bpmn-constructor/src/Editor.js` — редактор и ИИ-сценарии;
- `bpmn-constructor/src/App.js` — маршрутизация и защита маршрутов.

Тесты и сгенерированные артефакты внутри этих путей не становятся ядром
сами по себе.

### Обязательная дополнительная evidence

| Зона | Проверка |
|---|---|
| Скоринг (`core/bpmn_scoring.py`, `/api/evaluate`) | Прогон на эталонных схемах из `core/bpmn_dataset/` и на заведомо битом XML; балл и рекомендации соответствуют правилам |
| Генерация (`/api/generate`) | Запрос с типовым описанием → валидный XML → рендер и авто-раскладка в браузере |
| Улучшение и апрув (`/api/ai/improve`, `/api/ai/accept-improvement`) | Полный поток: предложение → сохранение `PendingImprovement` → принятие → обновлённая диаграмма; а также отказ от улучшения |
| Авторизация и доступ | `register` → `login` → защищённый вызов с токеном и без; чужая диаграмма/команда недоступны |
| Роли и команды | Поведение `admin`/`editor`/`viewer` для `editRegistry`, `manageRoles`; приглашение по токену и по домену |
| Общий доступ | Токен просмотра/редактирования, истечение срока, `can_edit` |
| Реестр и папки | Создание/перемещение/удаление/восстановление, дерево папок, командные диаграммы |
| Хранение и миграция схемы БД | `tests/test_migrations.py`: `upgrade head` поднимает всю схему, `alembic check` без отличий от моделей, легаси-база без `alembic_version` не «лечится» молча; старт приложения и целостность данных на копии рабочей `bpmn.db` |
| LLM-интеграция | Поведение при недоступном провайдере: понятная ошибка, ретраи не бесконечны |
| Frontend | `npm run build` без ошибок и браузерный сценарий при заметном UI-изменении |

Если существующей проверки на затронутое бизнес-правило нет, добавь
проверку полного потока либо явно зафиксируй ограничение в финальном
ответе.

## Тестировать функциональность, а не реализацию

Перед проверкой определи:

1. пользователя или потребителя сценария;
2. действие и входные данные;
3. бизнес-условия и права;
4. наблюдаемый результат;
5. поведение при ошибке, неполных данных или запрещённом действии.

Предпочитай публичный контракт: API-ответ, сохранённое состояние,
скоринг-результат, состояние интерфейса. Проверка внутреннего метода
дополняет, но не заменяет проверку целого сценария.

## Что проверять

- основной, пустой, неполный и ошибочный сценарии;
- граничные значения: очень большая схема, >50 элементов, отсутствие
  стартового/конечного события;
- авторизацию, роли, чужие объекты и истёкшие токены;
- сохранение в БД: запись, обновление, чтение, мягкое удаление
  и восстановление;
- конкурентные ситуации: повторное принятие приглашения или улучшения;
- генерацию и валидацию: некорректный, обрезанный и враждебный XML;
- деградацию при недоступном LLM-провайдере или SMTP;
- состояния фронтенда: загрузка, ошибка, пусто, успех.

## Тестовые данные

Для скоринга и улучшения сначала бери эталонные `.bpmn` из
`core/bpmn_dataset/`. Не используй реальные пользовательские схемы без
необходимости и не сохраняй чувствительные данные в документации.

## Backend-проверки

- Запусти приложение и проверь затронутый путь: endpoint → модель →
  `core/`-модуль → сохранение → ответ.
- Предпочитай проверку через API-границу, через которую запускается
  сценарий.
- Для изменений БД проверяй старт на чистой базе и на копии существующей
  (миграционная совместимость).
- Для изменений `core/` проверяй результат на нескольких схемах корпуса,
  а не на одной.

## Frontend-проверки

- Запускай `npm run build` в `bpmn-constructor/`.
- Проверяй пользовательский сценарий от действия до видимого результата.
- Для заметного UI-изменения проверяй экран в браузере на обычном
  и узком viewport.
- Проверяй маршруты, защиту `ProtectedRoute`, состояния загрузки, пустого
  результата и ошибки.
- Для редактора проверяй рендер схемы, авто-раскладку и сохранение.

## Документационные проверки

Для README, AGENTS и guideline-файлов проверь поиском:

- соответствие маршрутов фактическим маршрутам в `App.js`;
- соответствие продуктовых блоков фактическим endpoint-ам;
- упоминания удалённых файлов и механизмов как актуальных;
- терминологию из `product.md`.

## Финальный ответ

Укажи, что изменено, какие файлы затронуты, какие проверки выполнены
и почему какая-либо ожидаемая проверка не выполнялась.
