# BPMN-платформа ВкусВилл

Внутренняя экосистема бизнес-процессов: единое окно работы с BPMN-схемами и
единая точка их оптимизации. Схема генерируется по текстовому описанию через
ИИ, дальше её оценивает rule-based скоринг, а узкие места предлагаются к
исправлению операциями над XML — без генерации схемы целиком.

## Возможности

- **Генерация схем по описанию** — чат с LLM, потоковый вывод рассуждений,
  валидация структуры и формата BPMN.
- **Поиск узких мест и улучшение** — скоринг качества схемы + пакет операций
  правки (`core/bpmn_edits.py`), RAG по корпусу из 367 эталонных BPMN-схем.
  Принятие/отклонение предложения фиксируется как решение со статусом.
- **История версий схемы** — все правки хранятся последовательно, любую
  версию можно восстановить.
- **Командная работа** — команды, роли и приглашения по рабочей почте,
  реестр схем с папками, совместный доступ по ссылке (по умолчанию — только
  просмотр).
- **Апрувы изменений** — делегирование работы через роли и прием приглашений.

## Архитектура

```
main.py                  shim: uvicorn main:app
app/                     backend (FastAPI + SQLAlchemy)
  routers/               домены: auth, diagrams, folders, sharing, teams, ai
  services/              доступ, история версий, статусы решений об улучшении
  config.py              весь конфигурационный ввод — из окружения
core/                    AI-ядро
  bpmn_generator.py      генерация схемы, bpmn_scoring.py — скоринг
  llm_improve.py         улучшение, bpmn_edits.py — операции над схемой
  llm_client.py          транспорт и разбор ответов (GigaChat)
  bpmn_dataset/          корпус эталонов для RAG
bpmn-constructor/        frontend: React (CRA) + bpmn-js 18
  src/styles/tokens.css  дизайн-токены, вся вёрстка на них
tests/                   pytest: HTTP-контур, скоринг, аплайер операций, миграции
migrations/              Alembic (версионируемая схема)
```

СУБД задаётся `DATABASE_URL`: PostgreSQL — целевой режим, SQLite — легаси для
локальной разработки. Секреты (`SECRET_KEY`, SMTP, `GIGACHAT_CREDENTIALS`) читаются
только из окружения, в код не попадают. Локальный `python main.py` подхватывает
`.env` из корня проекта; в контейнер переменные передаёт compose.

## Запуск через Docker Compose

```bash
cp .env.example .env      # заполнить SECRET_KEY, POSTGRES_PASSWORD, GIGACHAT_CREDENTIALS
docker compose up -d      # backend 127.0.0.1:8765, frontend 127.0.0.1:3456
```

Схема поднимается миграциями Alembic, предопределённые роли сидируются при
старте, БД наружу не публикуется.

## Запуск локально

```bash
python -m venv .venv && .venv/Scripts/activate   # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
SECRET_KEY=... DATABASE_URL=sqlite:///./bpmn.db python main.py   # порт BACKEND_PORT, по умолчанию 8765

cd bpmn-constructor && npm install && npm start                  # dev-сервер на 3456
```

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | строка подключения SQLAlchemy (PostgreSQL или SQLite) |
| `SECRET_KEY` | подпись JWT; обязателен при работе с PostgreSQL |
| `GIGACHAT_CREDENTIALS`, `GIGACHAT_SCOPE`, `GIGACHAT_VERIFY_SSL`, `GIGACHAT_MODEL`, `GIGACHAT_MAX_CONCURRENT` | провайдер LLM (GigaChat) |
| `AI_MAX_XML_CHARS`, `MAX_UPLOAD_BYTES`, `AI_REQUESTS_PER_HOUR` | лимиты ИИ-контура: размер схемы, размер загрузки, часовой бюджет запросов на пользователя |
| `MAIL_*` | SMTP для приглашений и сброса пароля |
| `BACKEND_PORT`, `FRONTEND_URL`, `REACT_APP_API_URL` | порты и адреса локального запуска |

Полный шаблон — `.env.example`. `GIGACHAT_MODEL` — имя модели или пул через
запятую (следующую модель просят, когда провайдер не знает текущей); пусто —
пул по умолчанию из `core/llm_client.py`.

## Тесты

```bash
python -m pytest tests/ -q
```

1196 тестов: разбор ответов LLM и пул моделей (404 «No such model» — переход к
следующей, транспортный сбой — нет), генерация структуры в две стадии (сначала
состав: роль обязана назвать хозяина; затем маршрут внутри утверждённого
состава), починка плана (пустые пулы, кому принадлежат шаг и роль, потерянный в
описании участник), слияние «ролей-пулов» в дорожки, вставка шлюзов схождения и
развилки по условиям веток, аплайер пакета операций (новый узел с обеими дугами,
межпуловая нога — поток-сообщение, откат шагов вне маршрута и откат пакета с
незащищённым циклом), целостность `attachedToRef`, RAG-поиск по 367 эталонам,
скоринг по 26 правилам, HTTP-контур генерации/улучшения/принятия, все маршруты
(включая импорт `.bpmn` и сброс пароля), миграции схемы, метрики харнесса и
гигиена текста исходников. Сеть и ключ LLM не нужны — LLM подставлен на уровне
транспорта. Прогон на PostgreSQL — переменной `TEST_DATABASE_URL`.

## Как устроена генерация и улучшение схем

Генерация идёт в две стадии, и это не косметика: выдумывать содержание нельзя,
поэтому состав утверждается раньше маршрута.

1. Модель описывает состав (`actors`, `participants`, роли с `inside`) —
   план-гейт проверяет, что каждая действующая сила описания стала пулом или
   дорожкой, и задаёт узкий вопрос о принадлежности вместо переписывания плана.
2. Внутри утверждённого состава модель строит маршрут; повтор принимается только
   если он не ухудшил профиль нарушений (число нарушений по классам важности).
3. `repair_structure` доводит ответ до валидной схемы детерминированно: пустые
   пулы, недостижимые узлы, одниходовые шлюзы, отсутствие ветки обработки у
   таймера. Каждый шаг починки пишется в `trace` — «добавлено» считает только то,
   чего в ответе модели не было.
4. Дальше схема скорится по 26 правилам и отдаётся пользователю с текстом
   нарушений и рецептами правок.

Улучшение работает пакетом операций (`core/bpmn_edits.py`), а не перегенерацией
XML: 20 операций с словарём `OP_SPEC`, который рендерится в промпт дословно, и
`OP_ALIASES` для синонимов. Пакет применяется гарантом `apply_and_guarantee`
(применение → починка до покоя → снятие осиротевших узлов → отказ всему пакету →
сверка отчёта с вернувшимся XML), затем корректирующий повтор закрывает то, что
не применилось. Принятие изменений пересчитывает балл и показывает дельту по
правилам.

## Харнесс `eval/`: что и как измеряется

```bash
python -m eval.run --mode replay                 # детерминированно, годится в CI
python -m eval.run --mode live --repeat 3        # настоящий GigaChat, виден разброс
python -m eval.run --mode replay --fail-on-regression
python -m eval.run --dump-schemes DIR            # схемы прогона с вердиктом в имени
```

Оракул независим от продуктового скоринга: `eval/invariants.py` читает только
XML (13 инвариантов нотации + 5 бизнес-правил), иначе правка скоринга двигала бы
и линейку, и измеряемое значение. Три переписи мерят саму линейку:
`python -m eval.coverage` (чем правила смотрят на реальные схемы и где скоринг
расходится с оракулом), `python -m eval.advice --all-rules` (исполним ли совет по
тем id, которые называет) и `python -m eval.retrieval` (подбор эталонов RAG).
Провенанс (`eval/provenance.py`) не даёт метрике считаться на утечке: кейс,
пересекающийся с few-shot образцом промпта, — дефект измерения.

Планка — сводная доля пройденных гейт-проверок одной схемы,
`quality/scheme_checks_share` ≥0.8 в обоих режимах. Конъюнкционные строки
(`pass@1/scenario` и пара им) сняты: при ~17 проверках на схему произведение
независимых условий даёт 0.06 при 15% проваленных проверок — это геометрия
произведения, а не оценка контура. Факт «схема без единого провала» остался в
кейсе и в имени файла `--dump-schemes`.

| метрика | вопрос | replay | live #63 |
|---|---|---|---|
| `quality/scheme_checks_share` | какая доля гейт-проверок пройдена на схеме | 0.929 | 0.879 |
| `quality/structure_checks_share` | то же по плану, до генерации XML | 0.929 | 0.879 |
| `quality/business_checks_share` | то же по бизнес-слою (вне планки: эталон сам держит узкое место) | 0.833 | 1.062 запаха на схему |
| `improve/scheme_checks_share` | доля пройденных проверок после пакета | 0.982 | 0.903 |
| `improve/base_checks_share` | та же мерка на базовой схеме (пара к предыдущей) | 0.910 | — |
| `improve/defects_repaired` | что пакет убрал из дефектов базы | 0.667 | 0.275 |
| `improve/business_repaired_share` | то же по узким местам процесса | 0.667 | 0.467 |
| `improve/op_acceptance` | доля операций, реально изменивших схему | 0.917 | 0.567 |
| `improve/redundant_refusals_share` | из них — отвергнутых как «уже сделано» | — | крупнейший класс (33/121 в #61) |
| `improve/retry_gain` | долю отказов первого раунда, закрытых повтором | — | 0.357 |
| `business/scorer_oracle_agreement` | согласны ли два слоя на одной схеме | 1.0 | 1.0 |
| `improve/base_advice_drift` | по скольким советам пакет строился вслепую | 0.0 | 0.0 |

Правила чтения чисел, запертые тестами. Доля прохождения сама по себе не
отличает схему без подсказок от схемы с ними — для этого `--dump-schemes`.
Baseline сопоставим только внутри своего режима (live против replay-baseline даёт
девять ложных регрессий), а слепок без отпечатка линейки (`ruler`) сверяется, но
смена состава правил объявляется отдельно. Падение метрики — не всегда регрессия
контура: оно же может означать, что измерение переставало быть честным. Так было с
`improve/retry_gain`, которая отдавала абсолютное число закрытых повтором отказов
и агрегировалась средним: 0.0 читалось как «повтор бессилен», а в долях тот же
прогон даёт 0.357. Так же было с атрибуцией прогона #53, где «отвергнутый
переспрос» приписывался контуру и тогда, когда второй ответ не принёс ничего.
Снятые метрики не молчат: `unverified_metrics` называет ключи, которые нечем
сверить, иначе снятая метрика выглядела бы как «всё сверили, регрессий нет».

## Известные ограничения

- `pass@1/expected_participants` в live держит разброс 0.25–0.81 на неизменном
  коде: модель не заводит пул для действующего лица, даже когда узкий вопрос ей
  задан. Правки, которые это «чинили» (оставление пустого пула, распознавание
  имён в начале фразы), измерение ухудшили и откатаны; дальше только наполнение
  пула, а не перенос дефекта между инвариантами.
- CORS открыт wildcard вместе с `allow_credentials` — закрывается списком из
  окружения одновременно с refresh-токенами.
- Кэш ответов LLM и вынос долгих ИИ-вызовов в воркер спроектированы, но не
  реализованы: `docs/plans/redis-cache-and-task-routing.md`.
- Планы по реархитектуре frontend и backend — в `docs/plans/`.
