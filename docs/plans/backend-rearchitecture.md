# Реархитектура приложения: слои, версии схем, очередь ИИ-задач

Статус: принято к работе 2026-09-20. Объём согласован с заказчиком:
фундамент + версии/апрувы + очередь ИИ-задач; из фронтенда — только
сохранение раскладки DI.

## Что уже корректно и не переписывается

`core/` — границы модулей верные: `llm_client.py` (транспорт, ретраи, разбор
враждебного ответа), `bpmn_edits.py` (домен правок: инвентарь, аплайер
операций, починка), `llm_improve.py` (планирование пакетом операций),
`bpmn_generator.py` (один structured-output вызов), `bpmn_scoring.py`
(эвристика). Схема «модель предлагает операции → код применяет
детерминированно → семантическая починка» и есть нужная архитектура для
LLM-фич; узкое место не в ней.

## Точки, где архитектура перестала обслуживать задачу

1. Версионирования нет вообще: `git rev-parse` — не репозиторий, CI нет,
   Alembic нет, `create_all` + `apply_migration()` + сид ролей исполняются
   на импорте модуля (`main.py:388-395`).
2. `main.py` = 1850 строк, 42 эндпоинта в одном модуле: модели, схемы,
   авторизация, команды, папки, шеринг, SMTP и ИИ вперемешку.
3. «Апрув изменений» без истории: принятие перезаписывает
   `diagrams.xml_content` и удаляет `PendingImprovement` — ни отката, ни
   аудита, ни защиты от гонки в командной работе.
4. Долгий ИИ-вызов живёт в запросе (`asyncio.to_thread` в обработчике) —
   см. `docs/plans/redis-cache-and-task-routing.md`.
5. Скоринг содержит непроверяемое правило `direction`, которое безусловно
   даёт 8 баллов, и «починку», вписывающую `conditionExpression=true` как
   заглушку: headline-метрика поддаётся накрутке.

## Целевой вид

```
app/
  settings.py     # pydantic-settings; SECRET_KEY обязателен вне SQLite
  db.py           # engine, SessionLocal, Base — без побочного create_all
  models.py       # + DiagramVersion, + ai_tasks (этап B)
  schemas.py      # pydantic-контракты
  security.py     # bcrypt, JWT, сброс пароля
  deps.py         # get_db, get_current_user, проверки доступа к диаграмме
  services/       # доступ, реестр, команды — чистая бизнес-логика, тестуема
  routers/        # auth, users, diagrams, folders, teams, sharing, ai, export
  main.py         # create_app(); lifespan: схема БД, сид ролей, прогрев ИИ
main.py           # шим `from app.main import app` (uvicorn/Docker не меняем)
core/             # без изменений по границам
```

Контракт API (пути, тела, коды) сохраняется: фронтенд в этом объёме не
трогаем, кроме раскладки DI.

## Решения, зафиксированные явно

- **Совместимость при этапе B.** Дизайн-план предписывает ломать контракт
  (`202 + task_id`) и переводить фронт на опрос. Заказчик ограничил
  фронтенд раскладкой DI, поэтому веб-процесс ставит задачу в очередь и
  **ждёт** результат с ограниченным таймаутом, отдавая прежний JSON;
  `GET /api/tasks/{id}` появляется сразу, перевод UI на поллинг — отдельный
  шаг по явному согласию. Синхронный фасад — временный: он сохраняет
  идемпотентность, лимит параллельных LLM-вызовов и кэш, но не решает
  таймауты прокси до переключения фронта.
- **История важнее экономии строк.** `PendingImprovement` перестаёт
  удаляться: статус `approved|rejected|superseded` — это и есть продукт
  («апрувы изменений»), а не техническое состояние.
- **Геометрия не проверяется без DI.** Бэкенд отдаёт семантику без DI
  (решение предыдущей итерации), поэтому правила, зависящие от координат,
  с бэкенда снимаются полностью, а не имитируются.
- Секреты только из окружения; `.env`, `bpmn.db` и pickle-кэши в
  `.gitignore`; ранее попавшие в код значения считаются скомпрометированными.

- Полный переезд фронтенда на Vite и приборка UI-китов (Chakra + PrimeReact
  + три набора иконок + дубль `bpmn-auto-layout` в package.json) — в этой
  области работает параллельная сессия, см. `frontend-redesign-and-stability.md`.

  `allow_origins=["*"]` вместе с `allow_credentials=True` (`main.py:66-72`),
  соответствие `OAuth2PasswordBearer(tokenUrl="api/login")` фактическому
  JSON-логину.
- Evals-набор на ИИ-выходах (качество планов операций на корпусе эталонов).
