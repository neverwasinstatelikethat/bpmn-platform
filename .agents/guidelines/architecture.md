# Architecture Rules

## Когда использовать

Открывай этот файл для задач по архитектуре, документации, потокам данных,
интеграциям, границам модулей и планированию миграций хранилища.

## Актуальный контур

- FastAPI-пакет `app/`: `main.py` — только составной корень (lifespan,
  middleware, подключение роутеров), `routers/` — API по доменам,
  `models.py`/`schemas.py`/`security.py`/`deps.py`/`db.py`/`config.py`/
  `mailer.py`/`ai.py`/`startup.py` — соответствующие слои;
  `app/services/` — то, что должно совпадать во всех endpoint-ах:
  `access.py` (объектный доступ), `versions.py` (история схемы),
  `improvements.py` (статусы решений об улучшении); корневой
  `main.py` оставлен тонким шимом (`from app.main import app`), чтобы
  `uvicorn main:app` и Dockerfile не менялись;
- SQLAlchemy (declarative); БД задаётся `DATABASE_URL`: SQLite для
  легаси-разработки, PostgreSQL — целевой источник истины; секреты и
  настройки читаются из переменных окружения;
- миграции схемы — Alembic (`alembic.ini`, `migrations/versions/`);
  `run_migrations()` в `app/startup.py` доводит базу до `head` на старте
  процесса, сидирование ролей — `seed_default_roles()`;
- AI-ядро в `core/`: `bpmn_generator.py` (генерация), `bpmn_scoring.py`
  (скоринг), `llm_improve.py` (оркестратор улучшения: RAG + LLM → пакет
  операций), `bpmn_edits.py` (инвентарь схемы, детерминированный аплайер
  операций, семантическая починка), `llm_client.py` (транспорт, ретраи,
  разбор «непослушного» ответа);
- RAG-корпус `core/bpmn_dataset/` (сотни эталонных `.bpmn`) и pickle-кэши
  индексов (`bpmn_rag_cache.pkl`, `bpmn_agent_cache.pkl`);
- LLM через OpenAI-совместимый клиент (Foundation Models API,
  `openai/gpt-oss-120b`);
- email через fastapi_mail (настройки из окружения) — приглашения и сброс пароля;
- статика и артефакты экспорта в `static/`;
- frontend: React (CRA) + bpmn-js в `bpmn-constructor/`, адрес backend
  задаётся `REACT_APP_API_URL` (по умолчанию `http://localhost:8765`).

Docker Compose-контур (`docker-compose.yml`, `Dockerfile`,
`bpmn-constructor/Dockerfile`) обкатан: `db` (PostgreSQL), `backend` и
`frontend` поднимаются `docker compose up -d`, backend доступен на
`127.0.0.1:8765`, frontend — на `127.0.0.1:3456`. Данные перенесены из
`bpmn.db` в PostgreSQL. Очереди задач пока нет; автотесты — `pytest tests/`
и конвейер `.github/workflows/ci.yml`.

## Целевой контур (дорожная карта)

- Источник истины — PostgreSQL: подключение через `DATABASE_URL`
  реализовано, данные перенесены из `bpmn.db` скриптом
  `migrate_sqlite_to_postgres.py`, схема ведётся миграциями Alembic
  (`create_all` и ad-hoc `apply_migration()` убраны).
- Docker Compose обкатан: `db` (postgres, volume, healthcheck, без
  публикации наружу), `backend` (uvicorn, healthcheck `/health`),
  `frontend` (сборка + раздача через nginx), секреты из `.env`.
- Адрес backend для фронта задаётся переменной окружения сборки
  (`REACT_APP_API_URL`) и единым `src/config.js`, а не литералом
  в компонентах.

## Продуктовые границы

Рассматривай архитектуру через следующие блоки:

- генерация схем через ИИ;
- редактирование (bpmn-js) и импорт/экспорт;
- скоринг качества;
- улучшение через ИИ и апрув изменений;
- реестр бизнес-схем: диаграммы, папки, команды;
- доступ: роли, приглашения, общий доступ по токену;
- аккаунт: регистрация, вход, профиль, восстановление пароля;
- справочные разделы (гайдлайны, типовые ошибки).

Не выделяй внутренний модуль (`core/`-механизм, кэш, почтовый клиент)
как самостоятельный пользовательский раздел.

## Потоки данных

- Генерация: текстовое описание → `core/bpmn_generator.py` → LLM →
  валидация/починка XML → frontend рендерит схему и применяет
  авто-раскладку (bpmn-auto-layout).
- Скоринг: XML → `BPMNScorer.evaluate()` → балл, рекомендации,
  оптимизированный XML.
- Улучшение: XML диаграммы → оркестратор `llm_improve.py`: RAG-поиск
  похожих схем по корпусу → LLM-анализ и рекомендации → валидация
  улучшенного XML → `PendingImprovement` в БД → пользователь принимает
  (`accept-improvement`) или отклоняет.
- Доступ: приглашение → письмо с токеном → принятие → запись
  в `team_members` с ролью.
- Диаграммы хранятся как XML-текст в БД; файлы экспорта — в `static/`.
- Frontend хранит только токен сессии и кэш интерфейса в браузере;
  серверные данные (реестр, команды) в браузере не хранятся.

## Как анализировать изменения

1. Начинай с этого файла, нужного guideline и фактической точки входа.
2. Через `rg` проследи вызовы: endpoint в `app/routers/*` → модели/хранилище →
   модули `core/` → потребители во фронтенде.
3. Монолит разложен на `app/`, но общей папки `services/` пока нет:
   проверь, нет ли уже функции с похожей ответственностью в другом
   router-е, прежде чем дублировать её.
4. Сначала оцени возможность расширить существующую границу. Выделяй новый
   модуль или router, когда это яснее разделяет ответственность, снижает
   связанность или упрощает тестирование.
5. Изменения, затрагивающие хранение или контракт ИИ-потоков, проверяй
   полным сценарием (см. `testing.md`, Core Boundary).
6. Решения, связанные с хранилищем, сверяй с целью перехода
   на PostgreSQL: не закрепляй SQLite-специфику в новом коде.

## Код и комментарии

- Сохраняй удачные существующие границы, но меняй их, когда этого требует
  более цельное и проверяемое решение в рамках задачи.
- Для продуктовых комментариев и внутренних docstring предпочитай русский
  язык; в инфраструктурном или стороннем контексте следуй языку соседнего
  кода.
- Комментируй только неочевидное бизнес-правило, ограничение, сложный
  алгоритм или вынужденный обход; объясняй «почему».
- Не добавляй комментарии, пересказывающие синтаксис, имя функции или
  очевидную операцию.

## Диаграммы и описания

- Для архитектуры и user flow используй Mermaid, если диаграмма упрощает
  понимание.
- Показывай web как пользовательский вход, а FastAPI, AI-ядро, БД,
  RAG-корпус и LLM-провайдера — как отдельные значимые блоки.
- В пользовательском описании предпочитай смысловые названия техническим
  путям.
